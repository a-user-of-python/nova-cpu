## Design awkwardness — read before J2–J4

1. **§7.1 as written does not compile.** "main.swift gains
   `--engine`; with jit it sets `cpu.requestedEngine`" — but
   main.swift is also compiled against the baseline and shipped
   cores (plain `gate`/`baseline`), which have no
   `requestedEngine`; a direct reference breaks the plain gate at
   build time. Implemented instead: run.sh passes
   `-D NOVA_JIT_ENGINE` to swiftc exactly when the variant dir
   carries `NovaJIT.swift`, and all JIT references in main.swift
   sit inside `#if NOVA_JIT_ENGINE`. `--engine jit` on a non-JIT
   binary is a usage error, never a silent fallback. J5 should
   expect the same shape when the app target gains the real API.
2. **`NovaJIT.lastProbe` has no honest pre-probe value.** The
   design names it a non-optional `JitAvailability`, but before
   the first probe neither `.available` nor any listed
   `.unavailable` reason is true. J1 adds one extra reason,
   `.notProbedYet`, as the initial sentinel only; `probe()` never
   returns it.
3. **The spike's RW+MAP_JIT fallback was dropped.**
   `JitCodeMemory` tries only the spike-proven RWX+MAP_JIT form
   for the MAP_JIT path (the RW fallback would additionally need
   an mprotect to become executable, which the spike never
   exercised). If RWX+MAP_JIT is refused, the MAP_JIT path simply
   fails and the probe moves to the next path.
4. **§5.1's `regs[0]…regs[15]` cannot be a Swift array** in a
   fixed-layout struct (Swift arrays are not fixed-layout).
   `JitState` realises them as fields `r0…r15` with array bridges
   in `syncIn`/`syncOut`. All fields are `UInt64` declared in
   offset order, which Swift lays out sequentially in practice —
   but Swift does not guarantee C struct layout, so **J2 must
   verify the offsets before generated code depends on them**
   (e.g. a one-time `MemoryLayout<JitState>.offset(of:)` check in
   the trampoline, or address slots by base + index arithmetic
   computed in Swift rather than baked constants).
5. **`run_one` cannot see the variant dir.** §7.1 says run_one
   passes `--engine jit` "when the binary under test was built
   from a directory containing NovaJIT.swift", but run_one's
   inputs are (binary, case, outdir) — the build dir is gone by
   then. Implemented with a `<binary>.engine` marker file written
   by `build_harness`/`build_harness_dir`. Consequence for J4:
   `speed.py` invokes binaries directly (not via run_one), so
   `speed-all` currently runs the jit variant binary as an
   interpreter (no `--engine` flag) — harmless in J1 (zero
   codegen) but **J4's speed table needs speed plumbing for the
   flag** or the JIT row will silently measure the interpreter.
6. **`activeEngine` never reads `.jit` in J1 — by design, but
   know it.** §2.3 defines it as what the run actually used; the
   J1 trampoline uses nothing, so a J1 indicator reads
   "interpreter" even with a successful probe. The value to watch
   in J1 is `NovaJIT.lastProbe`. J2 flips `activeEngine` only
   when the trampoline first genuinely drives a run — keep that
   discipline; an indicator that claims JIT for interpreter work
   would be worse than none.
