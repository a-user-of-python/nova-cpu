## 1. Coverage accounting — 93/93

J3 ended at 81/93 compiled. J4 adds the 10 remaining implemented
opcodes; ROLL/MEMCPY stay the design's named bails. Final state —
every opcode `step()` implements has exactly one named treatment:

| Treatment | Opcodes | Count |
|---|---|---|
| Inline, block continues | Stack 28 (00–1E implemented subset: 00,01,02,03,04,05,06,07,08,09,0A,0B,0C,0D,0E,10,11,13,14,15,16,17,18,19,1A,1B,1C,1D) + ALU 29 (40–4F,50–57,5C–60 as implemented) + memory RAM path 9 (80,83,84,85,86,87,88,89,8A) + CSRGET C6, RDCYCLE CC, CPUID F5 | 69 |
| Inline, block-terminating | Control flow 12 (A0,A1,A2,A3,A6,A7,A8,A9,AA,AB,AC,AD) + DSPSET 12, CSPSET 1E, CSRSET C7, MRET C2 | 16 |
| Native trap/halt exit | TRAP AE, ECALL C0, EBREAK C1 (fault exits via handleTrapAfterStep), WFI C5 (.wfi exit) | 4 |
| Helper callout (block continues) | RDTIME CB, RDRAND F4 | 2 |
| Named bail (single-step + J5 flush) | ROLL 0F, MEMCPY 8F | 2 |
| **Total** | | **93** |

Runtime-only exits (not opcodes): MMIO instances of 83/84/87/8A
peek-exit to a single-step (rule J3) — except a STORE8/STORE64 to
exactly the console address, which takes the D3 callout (§3);
the signed DIV/REM (INT64_MIN, −1) pair bails before the
instruction (design D2). Unimplemented opcodes (163 values) still
end the block before the instruction and are single-stepped, so
their `tval = opcode` / illegalInstruction state is the
interpreter's by construction.

Per-opcode notes for the J4 additions (semantics source of
truth: shipped `step()`, cross-checked against the variant's
`hotRun` mirror):

- **ECALL C0 / EBREAK C1** — compiled as fault exits (ecallU /
  breakpoint rawValues), pc = nextPc, no tval write — their whole
  semantics is the throw; the trampoline hands the trap to the
  interpreter's own `handleTrapAfterStep`, so ECALL vectoring
  (epc/cause push, status save, jump to timerVector) is the
  interpreter's code, not a re-implementation. galaxy's golden
  ends in ECALL and passes (§5).
- **WFI C5** — native `.wfi` exit: boundary counts it, stub sets
  pc = nextPc and returns reason .wfi; the trampoline clears
  `running` and ends the run — the state hotRun's halted path
  leaves. This removes the per-program final single-step (and,
  for shell-style workloads, every idle WFI round-trip).
- **MRET C2** — terminator: `status := savedStatus` in JitState,
  exit `.next` at the dynamic target `epc`. No flush: it writes
  no RAM and moves no stack pointer; the trampoline recomputes
  the §5.3 limit from the restored status at the next dispatch.
- **CSRSET C7** — terminator in the DSPSET/CSPSET shape minus
  the flush (same reasoning as MRET). Order mirrors step()
  exactly: the operand is baked at compile time; the value pop
  happens BEFORE the operand-validity fault, so an invalid CSR
  index still pops, then fault-exits illegalInstruction with
  pc = nextPc and no tval write.
- **CSRGET C6** — inline: operand 0/1/2 pushes epc/cause/status
  from JitState; any other operand fault-exits
  illegalInstruction with NO pop and NO tval write (step() pops
  nothing here), pc = nextPc.
- **RDCYCLE CC** — inline: pushes `JitState.cycle + delta`,
  where delta already includes RDCYCLE's own boundary increment
  — the same value step() pushes (its `cycle` after the fetch
  increment), per design §6.1.
- **CPUID F5** — inline compare chain on the popped leaf:
  0→0x4E564F41, 1→0x0200, 2→0b0111, 3→0x00312D61766F4E, else 0.
- **RDTIME CB / RDRAND F4** — helper callouts (design §6.4):
  generated code BLRs to @_cdecl Swift helpers whose bodies are
  the interpreter's exact host expressions —
  `UInt64(Date().timeIntervalSince1970 * 1_000_000)` and
  `UInt64.random(in: 0...UInt64.max)` — then pushes the returned
  value and the block continues. Call discipline: at an
  instruction boundary no guest value lives in a caller-saved
  register (dsp/csp/fp/delta/limit are callee-saved x20–x28 and
  survive by AAPCS construction); LR is saved in x29 (unused by
  codegen in a block body, callee-saved); host SP stays 16-byte
  aligned (prologue −96, never adjusted in a body). Helper
  addresses are baked into JitState slots by the trampoline per
  run. Non-deterministic by definition, as in the interpreter;
  no golden executes either (bench is speed-only and uses
  RDTIME — its deterministic section counts still verified, §5).

## 2. What did NOT change

- `ROLL 0F` / `MEMCPY 8F` remain named bails (design §6.5),
  single-stepped with a J5 flush.
- LOAD64/LOADU8 keep the J3 peek-exit for every MMIO address,
  including the console address: the console is write-only
  (`mmioRead` returns 0 for it and no handler runs), no workload
  in the repo loads from it, and the side-effecting MMIO reads
  (keyboard pop, live timerCount, file/net results) must keep
  the single-step path. D3-for-loads was judged not applicable.
- The timer-limit protocol, invalidation rules J1–J7, exit-stub
  folding, and the 64-instruction cap are unchanged from J2/J3.

## 3. D3 console callout — verdict: KEEP

**The experiment.** A compiled STORE8/STORE64 whose peeked
address is exactly `NovaMemory.consoleAddr`
(0xFFFF_FFFF_FFFF_0000), with the value slot also proven
readable (so both pops are known to succeed), no longer exits:
generated code pops both operands in step()'s order and calls a
Swift helper that performs the IDENTICAL
`NovaMemory.mmioWrite(consoleAddr, value)` — same handler, same
UTF-8 buffering, same `consoleOutput` callback; the only change
is who calls it. The block then continues: no exit, no flush.
Every other MMIO address (keyboard, file, timer, net) keeps the
J3 peek-exit + J5 flush, and a console address with an
unreadable value slot single-steps, so step() itself reproduces
the half-popped fault state. Why this is safe where a general
MMIO callout would not be: the console branch of mmioWrite
touches only the UTF-8 buffer and the callback — no guest RAM
(so no stale-code risk, no J1/J5 concern) and no timer field
(so the trampoline's §5.3 settling stays exact) — and it never
calls a checked accessor, so calling it inside `withHotBuffer`
cannot trip Swift exclusivity. Gated by
`NovaCPU.jitD3Enabled` / harness `--jit-d3 on|off` so the A/B
below is one binary, both settings.

**The numbers** (speed-all run 41901995849, §4; best of 5,
CI-runner host):

| Workload | D3 off (J3 peek-exit) | D3 on (callout) | Ratio |
|---|---|---|---|
| galaxy ips | 169,411 | 2,803,663 | **16.5×** |
| bench ips | 24,083,530 | 50,514,754 | **2.10×** |

Gate: gate-variant jit is green with D3 on (§5) — console bytes
bit-identical on every golden, selfmod included. Per the lane's
rule (keep only if gate-green AND measurably better), **D3 is
KEPT**: `jitD3Enabled` defaults to true, and the official JIT
rows in §4 are the D3-on rows. The design's D3 question is
closed: the per-character exit was indeed galaxy's dominant
cost (it also visibly taxed bench, whose console section prints
10,000 chars).

**Read this table plainly:** the JIT is exact (§5) and D3 is a
large win within the JIT, but on this dispatch the JIT engine
is SLOWER than the shipped hotloop interpreter on both headline
workloads (bench 0.23×, galaxy 0.36× the interpreter's ips).
This is the first honest JIT-vs-interpreter wall-clock
measurement — J2/J3 reported only guest-printed RDTIME rates
and stats, never harness wall time — and the gap is a
trampoline property, not a J4 regression: every block exit
(including every control-flow terminator; there is no in-cache
chaining, by design §6.2) round-trips through the Swift
trampoline with a full JitState sync-in/sync-out, so
branch-dense code pays that cost per basic block while hotloop
pays it per 8,192 instructions. Per design §7.2, whether a JIT
that is not faster than hotloop on bench ships is the
coordinator's judgement at this table; J5 (§7) is written so it
can proceed or wait on that call without rework. Nothing in J4
traded exactness for speed to chase this number.

## 6. Deviations / exclusions (with reasons)

1. **D3 also covers STORE64-to-console**, not only STORE8: the
   handler and the exactness argument are identical (mmioWrite
   takes the value; its console branch uses the low byte), and
   firmware-style code that stores a full word at the console
   address gets the same win. STORE8 remains the measured path
   (every console writer in the repo uses it).
2. **LOADU8/LOAD64 console reads not callouts** — judged not
   applicable (§2): write-only address, no handler, no workload.
3. **speed.py unchanged** — the bypass was run.sh not supplying
   engine arguments to a verbatim forwarder; fixed there (§4).
4. **CSRSET/MRET terminate without a cache flush** — they write
   no RAM and move no stack pointer, so J2's premise is intact;
   the trampoline's per-dispatch limit recomputation from entry
   status is what their semantics needs (J3 note flagged this
   shape; the gate, including the firmware smoke's timer/MRET
   traffic, is the proof).
5. **Firmware smoke is evidence, not a gate** — the shell is
   interactive with no golden; the step's claim is engine
   agreement only, and its result never changes the gate exit
   status (same pattern as the bench evidence step).
